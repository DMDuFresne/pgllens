# Tools

All 31 tools are read-only. Every tool returns markdown in the LLens envelope (see
[Response shape](#response-shape) below); errors come back as a fixed four-bullet block instead of
tracebacks or raw driver exceptions. Every tool declares `annotations` (`title`,
`readOnlyHint=true`, `idempotentHint=true`, `openWorldHint=false`: a closed world, one configured
database and its exposed schemas, not an unbounded set of external resources) and an explicit
`_meta.ui.visibility` (see [Tool visibility](#tool-visibility) below).

## Response shape

Every tool returns the same markdown envelope (full guide: [`STYLE.md`](STYLE.md)). This is the
real output of `list_tables` (test fixture; the timestamp and request id are frozen for the golden
test, not live values):

```text
## pgllens · list_tables
*catalog+stats · 2026-09-03T15:49:03Z*

| schema | table | kind | rows (estimate) | comment |
|---|---|---|---|---|
| `app_core` | `assets` | table | ~4.1K |  |
| `app_audit` | `events` | table | 82 |  |
| `app_core` | `sites` | table | 12 | Physical sites |
| `app_core` | `v_assets` | view | 0 |  |

---
3 tables · 1 views · ~4.2K rows (estimate)
*Next: describe_table(table="app_core.assets") · get_erd()*
```

Errors use the same header with `error` in the scope slot and exactly four bullets. This is the
real output of `get_query_store` when `pg_stat_statements` is not installed:

```text
## pgllens · get_query_store · error

- code: `EXTENSION_MISSING`
- message: extension `pg_stat_statements` is not installed on this database.
- hint: Run `CREATE EXTENSION pg_stat_statements;` as a superuser, then retry.
- request_id: `01TESTREQUESTID`
```

Codes: `QUERY_REJECTED`, `SCHEMA_UNKNOWN`, `TABLE_NOT_FOUND`, `FUNCTION_NOT_FOUND`,
`EXTENSION_MISSING`, `ARG_OUT_OF_RANGE`, `FORMAT_UNKNOWN`, `TIMEOUT`, `DB_ERROR`. The `request_id`
matches the server's JSON log line for the same call.

## Discovery

| Tool | Parameters | Returns |
|---|---|---|
| `list_tables` | `schema?` (default: all exposed) | Tables/views in the exposed schemas, with kind, row estimate, and comment. |
| `describe_table` ★ | `table`, `schema?` (default: all exposed) | Columns (type, nullability, default, comment, values) and primary key. An identity column (`GENERATED ALWAYS AS IDENTITY` / `GENERATED BY DEFAULT AS IDENTITY`) shows that clause in the default column instead of a blank. `values` shows an enum column's labels from the catalog, and for a non-enum column with ≤20 distinct values a sample of its most common values from planner statistics (approximate; needs `ANALYZE`, and says so when there are none), including when `n_distinct` is a negative fraction (Postgres's way of recording that distinct values exceed ~10% of rows), which is converted to an estimated count rather than dropped. A non-enum column whose name matches `REDACT_COLUMNS` shows no sampled values at all (blank cell, not `[masked]`); enum labels are metadata and still show. A name matching nothing in the exposed schemas reports "not found" with a suggestion, rather than an empty description. |
| `schema_overview` | `schema?` (default: all exposed) | Per-schema table/view counts and total row estimate, a quick orientation. |
| `refresh_schema` | none | Forces a re-read of the catalog, replacing cached schema metadata. Returns the number of tables/views now cached. |
| `search_columns` | `pattern`, `schema?` (default: all exposed) | Columns matching a case-insensitive substring, across every exposed schema (or one, if `schema` is given). |
| `get_sample_data` ★ | `table`, `limit=10` (1-1000), `schema?` (default: all exposed) | Up to `limit` unfiltered sample rows; columns matching `REDACT_COLUMNS` render as `[masked]`. Values outside 1-1000 are rejected, not clamped. Any cell longer than 2,000 characters is cut with a marker stating its full length; read long values in slices with `substr(col::text, 1, 2000)` via `query`. |
| `get_table_stats` ★ | `table`, `schema?` (default: all exposed) | Row count plus per-column null count/percentage and distinct-value count, plus min/max for numeric, date/time and money columns, batched into one `UNION ALL` query where possible; falls back to one query per column if a json/xml column can't support `COUNT(DISTINCT)`. A 0-row table lists every column with zero stats rather than dividing by zero. |

★ = **app-callable**: the only three tools the `get_erd_widget` drill-down drawer is allowed
to invoke itself via `tools/call`. Every other tool, including `get_erd` and `get_erd_widget`
themselves, is model-only;
see [Tool visibility](#tool-visibility) below.

## Business rules & structure

| Tool | Parameters | Returns |
|---|---|---|
| `get_ontology` | `schema?` (default: all exposed) | Semantic summary: which tables are hubs (most referenced), how tables connect, and naming conventions in use (soft delete, audit columns, lookup tables, junction tables), plus any operator-supplied domain context prepended. |
| `get_relationships` | `table?`, `schema?` (default: all exposed) | Foreign keys as a markdown table. With `table`, shows outgoing and incoming relationships for that table only. Foreign keys whose referenced table is outside `EXPOSED_SCHEMAS` are not listed. |
| `find_path` | `from_table`, `to_table`, `schema?` (default: all exposed), `max_hops=6` (1-10) | Shortest foreign-key join path between two tables, as numbered hops plus a ready-to-paste `FROM ... JOIN ...` clause with table aliases. Searches every exposed schema and treats each FK as traversable in either direction; equally short alternatives are listed after the chosen path. No path within `max_hops` renders a normal response with a tally of `0 paths` and a `Next:` line pointing at `get_relationships(table=<src>)` and `get_relationships(table=<dst>)`, not an error. Foreign keys whose referenced table is outside `EXPOSED_SCHEMAS` are not listed. |
| `get_erd` | `schema?` (default: all exposed), `tables?` (list or comma-separated string), `include_columns=true`, `max_nodes=60` (1-200), `format="mermaid"` (`mermaid`\|`text`), `depth=1` (1-3) | An entity-relationship diagram as text: a Mermaid `erDiagram` code block (`format="mermaid"`) or a markdown table/relationship listing (`format="text"`), plus table/edge counts and any truncation note. No MCP Apps binding of any kind, see [The ERD widget](#the-erd-widget). `tables` selects a subset and pulls in their FK neighbours; `depth` is how many rounds of neighbours to pull in (ignored without `tables`); `schema` filters to one schema; with neither, every exposed table is shown, truncated to `max_nodes` by FK degree. `format="widget"` is rejected with a pointer to `get_erd_widget`. |
| `get_erd_widget` | `schema?` (default: all exposed), `tables?` (list or comma-separated string), `include_columns=true`, `max_nodes=60` (1-200), `depth=1` (1-3) | The same diagram as an interactive MCP Apps widget (pan/zoom, drag, search, drill-down, copy-as-Mermaid), plus a markdown summary every host can read. A host that doesn't render MCP Apps still gets the markdown summary. Same `schema`/`tables`/`depth`/`max_nodes` semantics as `get_erd`; no `format` parameter. |

## Programmable objects

| Tool | Parameters | Returns |
|---|---|---|
| `list_functions` | `schema?` (default: all exposed) | Functions with name, arguments, return type, volatility, and comment. |
| `get_view_definition` | `view`, `schema?` (default: all exposed) | A view's (or materialized view's) full `CREATE VIEW` text and column listing. |
| `get_function_source` | `function`, `schema?` (default: default schema) | Full function/procedure definition, including all overloads. |
| `get_constraints` | `table?`, `schema?` (default: all exposed) | `CHECK`, `UNIQUE`, `EXCLUDE`, `PRIMARY KEY` and `FOREIGN KEY` constraints with their full `pg_get_constraintdef` text (`describe_table` shows only the PK); the `validated` column reads `yes` or `NOT VALID`, and FOREIGN KEY rows carry a `references` column naming the target as `schema.table` (the definition text omits the schema for targets on the search_path). Defaults to all exposed schemas; `table` narrows to one resolved table, `schema` to one exposed schema. |
| `get_triggers` | `table?`, `schema?` (default: all exposed) | User-defined triggers (internal FK-enforcement triggers excluded) with enabled state (`enabled`/`disabled`/`replica only`/`always`), the full `CREATE TRIGGER` text, and the `schema.function` each one calls. Defaults to all exposed schemas; `table`/`schema` narrow as for `get_constraints`. |

## Query execution

| Tool | Parameters | Returns |
|---|---|---|
| `query` | `sql`, `page=1` (1-10000), `limit?` (1-`MAX_ROWS`), `explain_first=false`, `max_estimated_rows?` | Runs a `SELECT`/`WITH` query, capped at `MAX_ROWS`; `limit` sets this call's page size (omit for the server maximum), `page` fetches later windows (the query must contain an `ORDER BY`; pass the SAME `limit` on every page of a run). Out-of-range `page`/`limit` values are rejected, not clamped. `explain_first=true` plans the query first and prefixes the result with the planner's estimated rows and cost (never `ANALYZE`). `max_estimated_rows` implies `explain_first` and REFUSES the query without touching data when the estimate exceeds it. Over-budget queries are also rejected when `MAX_ESTIMATED_COST` is set. Columns matching `REDACT_COLUMNS` render as `[masked]` (display masking by output-column name, not a security boundary). Any cell longer than 2,000 characters is cut with a marker stating its full length; read long values in slices with `substr(col::text, 1, 2000)` via `query`. |
| `validate_query` | `sql` | Checks the query is read-only and parses/plans, without executing it. |
| `explain_query` | `sql`, `analyze=false` | Estimated plan (`EXPLAIN (FORMAT JSON)`, never executes), or actual plan with runtime stats if `analyze=true` (executes the query). |

## DBA & Diagnostics

Point-in-time reads of `pg_catalog`/`pg_stat_*`, never cached. When the lens role lacks a
permission or a required extension isn't installed, the tool stays registered and visible and
returns an `EXTENSION_MISSING` error envelope (or a narrower-but-valid result for a missing grant)
rather than erroring or disappearing; see [Response shape](#response-shape) above.

| Tool | Parameters | Returns |
|---|---|---|
| `server_info` | none | Version, uptime, total connection count, and a curated slice of notable settings (memory, workers, planner cost, WAL level). |
| `get_active_sessions` | `include_idle=false`, `include_background=false` | Connected sessions from `pg_stat_activity`: pid, user, application, client address, state, backend type, wait info, running-query duration and text. Always excludes the tool's own connection and the server's other pooled connections (`application_name='pgllens'`); excludes non-client backends (autovacuum, walsender, etc.) unless `include_background` is true. |
| `get_blocking` | none | Sessions currently blocked on a lock, paired with their blocker(s) via `pg_blocking_pids()`, each query's text, and wait duration. `"No blocking detected."` when idle. |
| `get_wait_stats` | `include_background=false` | Active sessions grouped by `wait_event_type`/`wait_event` with a count, a point-in-time sample of `pg_stat_activity`, not a cumulative counter (PostgreSQL has no built-in wait-history accumulator without the `pg_wait_sampling` extension). Excludes non-client backends (autovacuum, walsender, background workers, etc.) unless `include_background` is true. |
| `get_index_health` | `schema?` (default: default schema) | Every index with scan count and size; call-outs for unused indexes (`idx_scan = 0`, excluding PK/UNIQUE constraint-backed indexes), invalid indexes (a failed `CREATE INDEX CONCURRENTLY` left behind), duplicate indexes (same table, identical column list, partial-index predicate and expression list), and foreign keys with no covering index on their leading column (foreign keys whose referenced table is outside `EXPOSED_SCHEMAS` are not listed). A caveat states since when scan counts have accumulated (database stats reset time, or server start when never reset); under 7 days the `unused` section carries a caveat not to drop on that evidence alone. When `schema` is defaulted and more than one schema is exposed, a caveat under the index table names the schemas not shown. |
| `get_table_health` | `schema?` (default: default schema) | Vacuum, wraparound and space health per table: live/dead tuple counts (a `rows (estimate)` column -- a planner estimate, not an exact count), dead-tuple percentage, `bloat est.` (catalog estimate: `relpages` vs. the pages `reltuples` and `pg_stats` widths predict; `n/a` until analyzed), `xid age` (`age(relfrozenxid)`; renders `-` for a partitioned parent, which has no `relfrozenxid` of its own), last autovacuum run (NULL reads as "never"). `needs attention` lists tables over 5% dead tuples; never vacuumed with actual churn (dead tuples present, or on PostgreSQL 13+ >1000 inserts since vacuum); xid age above 75% of `autovacuum_freeze_max_age`; and estimated bloat above 20% when the wasted space exceeds 10 MB. A `sequences near limit` section lists sequences in the schema past 50% of their range with the owning table, flagged past 80%. A caveat states the database-wide xid age as a percentage of the 2^31 wraparound ceiling. Same scope caveat as `get_index_health` when `schema` is defaulted. |
| `get_space_usage` | `schema?` (default: default schema) | Total/table/index size per table (`pg_total_relation_size`/`pg_relation_size`/`pg_indexes_size`, formatted with `pg_size_pretty`) plus overall database size. Same scope caveat as `get_index_health` when `schema` is defaulted. |
| `get_query_store` | `order_by="total_time"` (`total_time`\|`mean_time`\|`calls`\|`rows`), `limit=20` (1-100), `since?` (ISO 8601 timestamp, extension 1.11+ / PG17+) | Top statements tracked by `pg_stat_statements`: call count, total/mean execution time, rows produced, shared-buffer hit/read counts, and the first 120 characters of the query text (`…` marks truncation). A caveat under the table names the window the numbers cover ("Statistics since reset: ...", `pg_stat_statements_info.stats_reset`, extension 1.9+ / PG14+), so a cumulative total is never mistaken for recent activity. `since` filters to statements first seen at or after that timestamp (`stats_since`, extension 1.11+ / PostgreSQL 17+ only), and is echoed back in the tally when applied; on an older version it is ignored and a second caveat says so rather than silently dropping the filter. A non-ISO-8601 `since` is rejected with an `ARG_OUT_OF_RANGE` error envelope instead of a raw driver error. Needs the `pg_stat_statements` extension (`EXTENSION_MISSING` error if absent). |
| `list_hypertables` | none | TimescaleDB hypertables: time column, chunk interval, compression, policies/jobs, continuous aggregates, chunk statistics. Needs the `timescaledb` extension. |
| `list_extensions` | none | Installed PostgreSQL extensions with installed/available versions. |
| `list_roles` | `include_builtin=false` | Database roles: login/superuser/createdb/createrole flags, connection limit, role memberships, and table grants (via `aclexplode`) across all exposed schemas. Built-in `pg_*` roles and their grants are hidden unless `include_builtin=true` (a caveat reports how many were hidden); a role whose dominant privilege set covers more than half of its relations collapses to one summary row naming the schemas, with only the differing relations listed as additional rows below it. Never reports credentials. |

## The ERD widget

`get_erd_widget` is delivered as an
[MCP Apps](https://modelcontextprotocol.io/specification/draft/extensions/apps) widget
(SEP-1865): a self-contained, CSP-safe HTML view (`ui://pgllens/erd-widget`, no CDN, no framework)
with pan/zoom/pinch, drag, search, double-tap-to-zoom, drill-down, and a "Copy Mermaid" button.
It's registered on the MCP SDK's `Apps` extension (`mcp.server.apps`), which stamps the
tool-level `_meta.ui.resourceUri` binding on the `tools/list` entry, the spec's only binding.
Every successful call carries `structuredContent`, which the host delivers to the view over the
ui bridge (`ui/notifications/tool-result`), **plus** a result-level `_meta.ui.resourceUri` →
`pgllens://view/erd/{id}`, a per-call copy of the view with this call's graph baked in, which
is the binding claude.ai actually renders. The MCP Apps spec defines only the static tool-level
binding, but claude.ai does not render from it alone; without the result-level baked resource the
panel stays blank, so both are always present. The rejected/error path (bad arguments,
no matching tables, etc.) returns text only, no `structuredContent`, no result-level `_meta`.
Nothing is gated on client capabilities: the server runs streamable HTTP in stateless mode, where
the SDK hands every request `client_capabilities=None`, so such a gate could never pass.

The tool always returns a markdown summary (table/edge counts, the truncation note) so a host
that can't render widgets still gets a useful body, never an empty one assuming the widget will
show. For the full table/relationship listing or plain Mermaid, call `get_erd` instead.

**Drill-down.** Clicking (or tapping/Enter-activating) a table card opens a drawer with three
tabs (Sample rows 5/10/20, Columns, Statistics) fetched live from the server via
`tools/call`, the same three tools (`get_sample_data`, `describe_table`, `get_table_stats`) a
model would call, but invoked by the widget itself. Only those three tools are app-callable
(`_meta.ui.visibility` on every tool registration, `src/pgllens/annotations.py`); everything
else, including `get_erd`/`get_erd_widget` themselves and `query`, stays model-only: a view able to re-run arbitrary
SQL, or re-invoke the tool that produced it, is a risk this project isn't taking on for a "what's
in this table" drawer.

**Host requirements.** The diagram itself needs a host that negotiates the MCP Apps extension
(`ServerCapabilities.extensions`) to render at all; a host that doesn't negotiate it still gets
the full markdown summary from `get_erd_widget`, just not the interactive view. The drill-down drawer
additionally needs that host to support `tools/call` from within the rendered view, a host that
renders the widget but doesn't wire up `tools/call` will show the diagram with a working drawer
*shell* but no data once opened.

**Why there are two ERD tools.** `@apps.tool(resource_uri=...)` stamps a static, per-*tool*
`_meta.ui.resourceUri` on the tool's `tools/list` entry, the MCP Apps spec's required
negotiation binding, present on every call regardless of arguments, which is why a host flagged
*every* `get_erd` call (`format="text"`, `format="mermaid"`, even a rejected `format="png"`) as
"rendered a widget". Since that binding cannot be removed from the widget path without breaking
the widget, the plain-text answer moved to its own tool: `get_erd` is a plain `@mcp.tool` with no
ui binding and no result-level `_meta` (its structured output is the SDK's plain
`{"result": "<markdown>"}` wrapper, the same one every `-> str` tool here returns, which carries
no ui binding and is not a widget signal); `get_erd_widget` is the only tool with the static
tool-level binding, and the only one that also stamps the result-level `_meta.ui.resourceUri`
described above (`tests/test_tools_erd.py::test_wire_get_erd_has_no_widget_binding_and_get_erd_widget_does`
drives the real wire, `initialize` → `tools/list` → `tools/call`, to pin both halves).

Full architecture and visual detail on the widget's layout/mobile behavior lives in the code
comments of `src/pgllens/tools/erd.py`.

## Tool visibility

`_meta.ui.visibility` is stamped explicitly on **every** tool registration
(`annotations.py::visibility`), never left to default. The MCP Apps spec defaults an omitted
`visibility` to `["model","app"]`, every tool callable from a view, so an explicit stamp is
what makes the three-tool app-callable allowlist (`get_sample_data`, `describe_table`,
`get_table_stats`) safe by construction, rather than "safe until someone adds a tool and forgets
the default is wide open." `tests/test_tool_visibility.py` pins this: every tool must declare
`_meta.ui.visibility` explicitly, and only the three listed above may include `"app"`.

## The read-only gate

Every read path (`query`, `validate_query`, `explain_query`) runs the SQL through the same
read-only gate (`pgllens/database/safety.py`): it neutralizes string literals, quoted
identifiers, comments (including PostgreSQL's nested block comments), and dollar-quoted bodies,
then rejects anything that isn't a single `SELECT`/`WITH`/`TABLE`/`VALUES` statement, blocks
write/DDL/transaction-control keywords, and blocks read-shaped function calls that write, read
the filesystem, or hold a server-side lock/sleep (`setval`, `pg_read_file`, `dblink*`,
`pg_advisory_lock*`, `pg_sleep*`, etc.) even if embedded without a statement separator. This is
the **second** wall; the primary guarantee is every connection opening with
`default_transaction_read_only=on` (`config.py::conninfo`), independent of anything in
application code. See [`docs/runbook.md`](runbook.md#the-read-only-gate-rejects-a-query-that-looks-like-select)
for the exact shapes it rejects and why.
